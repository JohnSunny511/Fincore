# Fincore – Digital Banking System
**Phase 1 – Database Creation (Database First)**

**Technology:** ASP.NET Core Web API · C# · ADO.NET · SQL Server · Stored Procedures · Swagger

## 1. Database
Created SQL Server database `FincoreDB`.

## 2. Created seven tables

- **Customer** – Stores customer personal information such as name, age, email, phone and address.
- **Admin** – Stores administrator information such as name and email.
- **Login** – Stores username, password, registration ID and role for customer and admin authentication.
- **Account** – Stores bank accounts, account numbers, balances, account types and statuses.
- **Transactions** – Stores deposit, withdrawal and transfer records.
- **Ledger** – Stores debit and credit entries associated with financial transactions.
- **AuditLog** – Records important actions performed by customers and administrators.

## 3. Database design concepts

- Tables created without foreign key or CHECK constraints.
- `Customer`, `Admin` and `Login` separated to distinguish profile information from authentication credentials.
- `Login.reg_id` identifies the corresponding Customer or Admin based on `Login.role`.
- `Account.customer_id` identifies the customer who owns the account.
- `Transactions` records financial operations.
- `Ledger` records account-level debit and credit entries.
- `AuditLog` records important administrative operations.

## 4. Financial transaction concepts

- Deposits increase account balances and generate transaction and ledger records.
- Withdrawals decrease account balances and generate transaction and ledger records.
- Transfers update both accounts, create one transaction record and create two ledger records.
- Transfers will use SQL transactions to maintain atomicity and consistency.

## 5. Audit logging

Audit records will be inserted directly inside relevant stored procedures instead of using triggers.


## 6. Authentication design

- A shared Login table is used for Customer and Admin authentication.
- `reg_id` identifies the associated profile.
- `role` distinguishes Customer from Admin.
- JWT authentication and role-based authorization will be implemented in a later phase.


Customer registration
1. Customer submits their registration details.
2. We insert their information into the Customer table.
3. We create their login credentials in the Login table.
4. The reg_id in Login is set to the newly created customer_id.
5. The role is set to Customer.


Admin registration
1. Admin submits their registration details.
2. We insert their information into the Admin table.
3. We create their login credentials in the Login table.
4. The reg_id in Login is set to the newly created admin_id.
5. The role is set to Admin.


Login
1. The user submits username and password.
2. The Login table is checked.
3. If the credentials match, the system retrieves reg_id and role.
4. The API identifies the user.
5. Later, JWT will carry identity and role information for protected API access.


Account creation
1. A customer requests a new account.
2. The Account table receives a new record.
3. The account is associated with the customer through customer_id.
4. The account receives a unique account number and initial balance.



## 7. Implementation approach

Database First – Tables → Stored Procedures → Models → DB Classes → Controllers → Swagger Testing.



8. Created Stored Procedures

Created stored procedures for customer registration, admin registration and login authentication.

sp_CustomerRegister – Registers a new customer by inserting personal information into the Customer table and login credentials into the Login table.

sp_AdminRegister – Registers a new administrator by inserting admin information into the Admin table and login credentials into the Login table.

sp_Login – Validates the username and password and retrieves the associated reg_id and role.



9. Customer Registration – sp_CustomerRegister

Accepts customer details, including name, age, email, phone and address, along with username and password.

Inserts the customer details into the Customer table.

Retrieves the newly generated customer_id using SCOPE_IDENTITY().

Inserts the login credentials into the Login table.

Assigns the customer ID to Login.reg_id and sets the role to Customer.

Uses a SQL transaction to group the customer and login insert operations.



10. Admin Registration – sp_AdminRegister

Accepts admin name, email, username and password.

Inserts admin information into the Admin table.

Retrieves the newly generated admin_id using SCOPE_IDENTITY().

Inserts the login credentials into the Login table.

Assigns the admin ID to Login.reg_id and sets the role to Admin.

Uses a SQL transaction to group the admin and login insert operations.



11. Login Authentication – sp_Login

Accepts username and password.

Checks the Login table for matching credentials.

Retrieves reg_id and role if the credentials match.

Returns the associated user identity and role to the application.

Returns no records when the credentials are invalid.

13. SQL Transaction Usage in Registration

SQL transactions are used in customer and admin registration to group profile creation and login credential insertion.

BEGIN TRANSACTION starts the transaction.

COMMIT TRANSACTION saves both insert operations.

Transaction handling ensures the profile and login records are treated as a single operation.

Rollback and error handling will be incorporated to handle failed registration operations properly.

### Why DTOs (Data Transfer Objects) Were Used

DTOs (Data Transfer Objects) are used to transfer data between the client and the API without exposing the entire model class.

Instead of using a single model class for registration, login, and other API requests, separate DTOs were created for specific operations.

**Why DTOs were used instead of a single class:**

- **Control the data received:** Each API accepts only the fields required for that particular operation.
- **Avoid exposing unnecessary properties:** For example, during customer registration, the client does not need to send `customer_id`, since it is generated by the database.
- **Improve security:** Sensitive or internal properties can be excluded from request objects. DTOs help control what is exposed, although they do not replace proper security measures.
- **Separation of concerns:** Model classes represent the application's data structure, while DTOs define the data that an API accepts or transfers.
- **Maintainability:** If the database model changes, the API request structure does not necessarily have to change.

**Example:**

The `Customerclss` model contains properties such as `customer_id`, customer details and login-related properties. However, `CustomerRegisterDTO` contains only the fields required for customer registration.

This allows the API to receive only the necessary registration information and then map it into the model before passing it to the DB class.

**Implementation flow:**

`Client Request → DTO → Model → DB Class → Database`

DTOs were used for customer registration, admin registration and login to keep the API request structures specific to each operation.

11. Technical Decisions and Concepts
DTO Usage
DTOs are not mandatory for every API. They are used when structured request or response data needs to be defined, or when controlling which properties the client can submit or receive.
- No DTO: APIs such as Get Customer Accounts, Get Account Details and Get Account Balance require only a single ID, which can be passed through the URL and automatically mapped to a controller parameter by ASP.NET Core.
- DTO required: Create Account accepts structured request data (customer_id and account_type) through the request body, so AccountCreateDTO is used.
- Status update DTO: AccountStatusDTO restricts the request to the account status property.
DTOs are introduced when they provide meaningful separation between API requests/responses and the underlying models, rather than creating unnecessary classes for simple parameters.

Request DTOs control incoming data, while response DTOs can be used to control the data exposed by APIs. Response DTOs may become useful in later phases, particularly for transactions and account-related operations.
Use of var
The var keyword allows C# to automatically determine a variable's type from the value returned by an expression.

For example:
var accounts = dbobj.GetCustomerAccountsDB(customer_id);
Since GetCustomerAccountsDB() returns List<Accountclss>, the variable accounts is automatically treated as a List<Accountclss>.

This is equivalent to:
List<Accountclss> accounts = dbobj.GetCustomerAccountsDB(customer_id);
The DB method creates and populates the list of account objects, then returns it. The variable accounts stores the returned list.



Route Parameters and DTO Binding
In APIs such as account status updates, the account ID is passed through the URL (e.g., /Account/updatestatus/5), while the new status is sent through the JSON request body using AccountStatusDTO.
[HttpPut]
[Route("updatestatus/{account_id}")]

ASP.NET Core automatically maps the URL value to the controller's route parameter (account_id) and maps the JSON body to the DTO object. The controller then passes both values to the DB class.

This separates the resource being updated (identified by the URL) from the data being changed (provided through the DTO).

Phase 5: Fund Transfers

## 1. Transfer DTO
Created `TransferDTO.cs` to receive the source account ID, destination account ID, transfer amount and description.

The DTO ensures that the API accepts only the information required for a transfer.

## 2. Transaction Model
Reused the existing `Transactionclss.cs` model to represent transfer information. No additional model was required.

## 3. Stored Procedure – sp_Transfer
Created `sp_Transfer` to handle fund transfers between two bank accounts.

The procedure performs the following operations:

- Validates the transfer amount.
- Prevents transfers between the same account.
- Checks whether both accounts exist and are active.
- Checks the source account's available balance.
- Deducts money from the source account.
- Adds money to the destination account.
- Inserts one record into the Transactions table.
- Inserts two records into the Ledger table.

Used SQL transactions with `BEGIN TRANSACTION`, `COMMIT` and `ROLLBACK` to maintain consistency.

Used `UPDLOCK` and `HOLDLOCK` to protect account rows during transfer processing.

## 4. Database Class
Added `TransferDB()` to the existing `TransactionDBclss.cs`.

The method executes `sp_Transfer` using ADO.NET and retrieves the generated transaction ID.

## 5. API Controller
Added the Transfer API to the existing `TransactionsController.cs`.

## 6. API Endpoint
